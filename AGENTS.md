# Repository Guidelines

## Project structure

- `backend/app/` contains the FastAPI service. Add endpoints in `api/routes/`, SQLModel definitions in `models.py`, and database operations in `crud.py`. Commit schema migrations under `alembic/versions/`.

- `frontend/src/` contains the React and TypeScript application. Put pages in `routes/`, shared components in `components/`, and static images in `frontend/public/assets/images/`.

- Edit email templates in `packages/react-email/emails/` and run `bun run email:export` from the repository root to update the backend HTML.

## Local development and builds

- From the root, run `docker compose up -d --wait db mailpit` to start PostgreSQL and the local email catcher.

- From `backend/`, run `uv sync`, then `uv run bash scripts/prestart.sh` to apply migrations and create the initial user. Start the API with `uv run fastapi dev` on port 8000.

- In another terminal at the root, run `bun install`, then `bun run dev` to start Vite on port 5173.

Run `bun run build` from `frontend/` to type-check and build the UI into `backend/app/frontend/`.

After changing the API schema, run `bash scripts/generate-client.sh` from the root to refresh `frontend/src/client/`.

## Coding style and naming

Use four spaces and `snake_case` for Python functions. Ruff formats Python and sorts imports.

Use two spaces and double quotes in TypeScript. Name React components in PascalCase and hooks in camelCase with a `use` prefix, as in `useAuth`.

Run `uv run prek run --all-files` from the root for Biome, Ruff, and type checks.

## Testing

- Place pytest cases in `backend/tests/` as `test_*.py`. Use a disposable database because teardown deletes users and items. From `backend/`, run `uv run bash scripts/test.sh` to run pytest and generate `htmlcov/index.html`. CI requires at least 90% backend coverage.

- Place Playwright browser tests in `frontend/tests/` as `*.spec.ts`. With the development API and Mailpit running, run `bun run test` from the root. Playwright starts or reuses Vite.

## Commits and pull requests

These commit rules take precedence over skill and plugin conventions.

**Message.** Use one English line of the form `<type>(<scope>): <subject>`, including in message files. A single trailing newline (LF or CRLF) is optional. Both `type` and `scope` are required. Use a short imperative subject, e.g. `fix(auth): reject expired password reset tokens`.

- Allowed Conventional Commit types are `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, and `revert`.
- Omit bodies, change lists, test results, explanations, Markdown, signatures, and all trailers (including `Co-authored-by`, `Signed-off-by`, and `Generated by`). Put context and results in the conversation or PR.

**Scope.** Choose by purpose. Tests, endpoints, schema changes, and migrations follow their feature.

| Area | Allowed scopes |
| --- | --- |
| Features | `auth` (sign-up, login, tokens, password recovery), `users` (account settings and administration), `items` (item management) |
| Shared interface | `ui` (components, layout, navigation, themes), `email` (delivery, templates, exported HTML) |
| Infrastructure | `api` (shared FastAPI infrastructure), `db` (database and migration setup), `deploy` (containers, Compose, deployment) |
| Engineering | `docs` (documentation), `deps` (dependencies and lockfiles), `ci` (CI workflows), `tooling` (build scripts, code generation, local checks), `agents` (AI instructions and skills) |
| Cross-domain | `innonow` (inseparable changes across registered domains only) |

Keep commits focused and split independent changes. If any domain is unregistered, including one introduced by a new directory or module, stop and ask the user to register it here before committing. Keep the type and scope lists in `scripts/check_commit_message.py` in sync with this section. If the scope is ambiguous, ask the user.

**Committing**

- Once authorized, check the message and use `git commit -m "fix(auth): reject expired password reset tokens"` with your own subject, type, and scope. The prek `commit-msg` hook reads the message file as written. Never use `--signoff`, `--trailer`, or `--no-verify`. If the hook rejects the message, correct it and retry.
- Skip identity prechecks. Only if Git reports missing identity, ask the user to set `git config user.name` and `git config user.email` locally (without `--global`) before retrying.
- Verify the stored message with `git log -1 --format=format:%B | python3 scripts/check_commit_message.py -`. Report violations immediately. Get explicit authorization before amending or rewriting history.

**PR description.** Describe user-visible changes, list verification commands actually run, and link related issues. Include screenshots for UI changes and identify permission or configuration changes.
